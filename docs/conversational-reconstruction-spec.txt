THAWING MEMORY
BOUNDED CONVERSATIONAL RECONSTRUCTION SPECIFICATION

Status: Approved for implementation planning
Version: 1.0
Date: 1 September 2026
Related milestone: Kitchen Memory Reconstruction Loop
Supersedes: The single-turn rules in sections 5 and 16 of interaction-prompt-spec.txt


1. PURPOSE

The first live prototype proved that a user-authored memory can receive a provisional AI reflection, limitation note, and sensory question. Testing exposed a conceptual gap: the interface asks a useful follow-up question but gives the user no way to answer it.

The revised interaction will support a bounded conversation that helps the user formulate a working family recipe from their own fragments. The model may organise and reflect user-supplied details, but it must not supply missing cultural knowledge, invent measurements, or present a regional recipe as authoritative.


2. CORE PRINCIPLE

The user remains the source. The AI is a reflective interviewer and organiser.

Only details explicitly supplied by the user may become evidence in the working recipe. Previous AI reflections, questions, and interpretations must never be treated as facts merely because they appeared earlier in the conversation.


3. BOUNDED SCOPE

- The user begins with one memory fragment.
- The model returns a reflection, limitation, and one focused question.
- The user may answer up to three AI follow-up questions.
- After each response, the user may answer, skip, or build the working recipe.
- The user may build the recipe before reaching three follow-ups.
- After three follow-up answers, the interface asks the user to build the recipe or return to edit their fragments.
- Unlimited chat is outside the assessed prototype scope.
- The Kitchen remains the only functional domain.


4. INTERACTION STATES

State 1: Initial memory

The user supplies the first remembered fragment and requests a reflection.

State 2: Provisional reflection

The interface shows:

- Provisional AI reflection
- Why this may be incomplete
- AI question

Available actions:

- Answer this question
- Skip this question
- Build my working recipe

State 3: Follow-up answer

The user answers in a field labelled "Add another memory fragment." The interface must state that "I do not remember" is a valid answer. The submitted answer remains visibly user-authored.

State 4: Continued reflection

The model receives the original memory, the previous AI question, and the user's answer with explicit authorship labels. It returns a revised provisional reflection, limitation, and one new question. The earlier exchange remains available for review.

State 5: Working recipe

The model organises the user-supplied fragments into a structured working recipe. Missing information remains visible under "Still unknown." The output must not silently complete missing ingredients, quantities, timings, or steps.

State 6: Evaluation

The user may:

- Keep as a working reconstruction
- Edit in my words
- This does not fit
- Return to the conversation

State 7: Archive

The saved trace preserves the original memory, follow-up fragments, provisional AI responses, working recipe, user decision, and any user revision or correction.


5. FOLLOW-UP REQUEST CONTRACT

POST /api/reflect
Content-Type: application/json

{
  "cardId": "kitchen-instinctive-measures",
  "memoryFragments": [
    {
      "text": "User-authored memory text",
      "questionAnswered": "Empty for the first fragment"
    }
  ],
  "action": "continue"
}

Rules:

- memoryFragments must contain between one and four items.
- Each text value must contain non-whitespace content and remain within the existing memory limit.
- questionAnswered records AI context and must never be treated as user evidence.
- action must be continue or build.
- The server must not log memory fragments.
- The server must reject attempts to exceed the follow-up limit.


6. CONTINUE RESPONSE CONTRACT

{
  "type": "reflection",
  "reflection": "string",
  "limitation": "string",
  "question": "string"
}

The existing field validation and display limits remain in force.


7. WORKING RECIPE RESPONSE CONTRACT

{
  "type": "working_recipe",
  "recipe": {
    "dishName": "string",
    "rememberedIngredients": ["string"],
    "rememberedMethod": ["string"],
    "sensoryCues": ["string"],
    "familyNotes": ["string"],
    "stillUnknown": ["string"]
  }
}

Rules:

- dishName must use the user's wording or state "Name not yet remembered."
- Arrays may be empty when the user supplied no matching detail.
- Every positive claim must be traceable to a user fragment.
- stillUnknown must expose important missing recipe information.
- The output is labelled "Working Family Recipe" and "Built from your fragments."
- The interface must not label it authentic, complete, correct, or traditional.


8. MODEL BEHAVIOUR

For continue:

- Reflect only what the newest user fragment adds to the reconstruction.
- Keep earlier user fragments available as context.
- Ask one question about a missing ingredient, sequence, gesture, sensory cue, readiness cue, substitution, family term, or transmission detail.
- Do not repeat a question the user answered or skipped.
- Accept uncertainty and "I do not remember" without pressure.

For build:

- Use only user-authored fragments as recipe evidence.
- Organise rather than complete the recipe.
- Do not infer quantities, timings, ingredients, geography, identity, or authenticity.
- Put missing information in stillUnknown.
- Preserve Malayalam and transliterated words exactly as supplied.


9. ARCHIVE DATA PLAN

The next archive schema will use a new storage version so existing prototype traces remain readable.

Proposed storage key:

thawingMemory.archive.v2

Proposed entry additions:

{
  "memoryFragments": [
    {
      "text": "User-authored fragment",
      "questionAnswered": "AI question or empty string"
    }
  ],
  "aiResponses": [
    {
      "reflection": "string",
      "limitation": "string",
      "question": "string"
    }
  ],
  "workingRecipe": {
    "dishName": "string",
    "rememberedIngredients": [],
    "rememberedMethod": [],
    "sensoryCues": [],
    "familyNotes": [],
    "stillUnknown": []
  }
}

The implementation must either migrate version 1 entries or read both versions. It must not silently delete the traces already saved in the browser.


10. FAILURE AND CONTROL RULES

- A failed follow-up call must preserve every user fragment.
- Only the failed turn may be retried.
- Repeated clicks must not create duplicate turns.
- Changing an earlier fragment invalidates all later AI responses and the working recipe.
- The user must explicitly choose when to build the recipe.
- The user must be able to return from recipe evaluation to the conversation.
- Skipping a question records no invented answer.
- The model call retry remains limited to one retry for temporary provider failures.


11. ACCEPTANCE CRITERIA

The conversational revision is complete when:

- The original one-turn path still works.
- A user can answer at least one AI question.
- The interface supports no more than three follow-up answers.
- Every user and AI turn is visibly labelled by source.
- The user can skip a question without supplying content.
- The user can request a working recipe at any supported turn.
- The working recipe contains only user-supplied details and visible unknowns.
- The user can keep, edit, reject, or return to the conversation.
- The full trace persists after refresh.
- Existing version 1 archive entries remain available.
- Loading and failure states preserve the conversation.
- Lint and production build checks pass.


12. IMPLEMENTATION SEQUENCE

Each step ends with inspection, one commit, and one push.

1. Conversation data model and pure helper functions.
2. Server validation for memoryFragments and action.
3. Continue prompt and structured reflection response.
4. Follow-up answer, skip, and turn-limit interface states.
5. Working recipe prompt and structured response validation.
6. Working recipe display and evaluation controls.
7. Archive version 2 persistence and version 1 compatibility.
8. Prompt tests for invention, skipped questions, uncertainty, and source separation.
9. Styling, responsive treatment, accessibility review, and documentation.
