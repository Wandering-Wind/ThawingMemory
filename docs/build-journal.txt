ENTRY 001

Date: 31 August 2026
Planned task: Define the prototype scope before visual design or implementation.
What was completed: A lean prototype PRD and an interaction and prompt specification were created. The assessed milestone was reduced to one complete Kitchen memory loop.
Choices made and why: The user memory comes before AI output. The model produces only a provisional reflection, limitation note, and follow-up question. Keep, edit, and reject choices keep the user active, while the original model response remains visible for accountability.
What failed, changed, or surprised me: The original proposal planned three functional domains. The narrower milestone better matches the assessment requirement for one reliable core interaction.
Evidence, such as commit, screenshot, prompt output, or bug: docs/prototype-prd.txt and docs/interaction-prompt-spec.txt. Commit to be added.
Next small step: Review and commit the planning documents, then remove the Vite demonstration content and create the unstyled landing-page shell.


ENTRY 002

Date: 31 August 2026
Planned task: Review the complete static interaction from the landing page to a saved Living Archive entry.
What was completed: The landing, Kitchen form, empty validation, static AI response, keep/edit/reject controls, local saving, Archive rendering, and persistence after refresh were tested as one continuous browser flow.
Choices made and why: The test used fictional memory text. The original AI response remained visible while user-authored revisions and corrections were displayed first in the Archive.
What failed, changed, or surprised me: An edited trace could initially be saved without changing the AI text because the edit field was prefilled. This could incorrectly label unchanged AI writing as the user's version. Save validation was changed so an edited trace must differ from the original AI reflection.
Evidence, such as commit, screenshot, prompt output, or bug: Browser review completed with no console warnings or errors. The validation change is in src/pages/Kitchen/KitchenPage.jsx. Commit to be added.
Next small step: Define and apply the prototype visual system to the complete static loop.


ENTRY 003

Date: 1 September 2026
Planned task: Establish and verify the local reflection endpoint before connecting Gemini.
What was completed: A Node HTTP server now accepts POST requests at /api/reflect, validates the known card ID and memory, enforces request and memory limits, and returns a clearly temporary three-field response.
Choices made and why: Node's built-in HTTP and fetch-compatible environment were selected to avoid adding a server framework for one prototype endpoint. The React client remains disconnected until the server contract and Gemini response are independently reliable.
What failed, changed, or surprised me: A previous test server continued holding port 3001 after its terminal session ended. Windows blocked detailed process inspection without elevated access, so the updated endpoint was safely verified on port 3002 instead of expanding permissions.
Evidence, such as commit, screenshot, prompt output, or bug: Valid request returned 200. Empty memory, unknown card, overlong memory, invalid JSON, oversized payload, and wrong HTTP method returned the intended structured errors. The server log did not contain submitted memory text. Commit to be added.
Next small step: Create a Gemini API key locally and replace the temporary server response with validated live model output.


ENTRY 004

Date: 1 September 2026
Planned task: Connect the static Kitchen loop to a live free generative model and verify the assessed core interaction.
What was completed: Gemini 3 Flash Preview now returns a validated reflection, limitation, and sensory question. The React interface calls the local server, preserves memory through failures, retries temporary provider errors once, and saves completed traces to the Living Archive.
Choices made and why: The API key remains in the local server environment. Gemini 3 Flash Preview was selected because it worked through the free AI Studio project. A second provider was deferred because a reliable primary loop, clear error handling, and source separation were more important than adding another integration.
What failed, changed, or surprised me: Gemini 2.5 Flash-Lite appeared in the model list but generation returned provider errors for the project. Gemini 3 Flash Preview initially returned temporary 503 errors, so one controlled retry was added. A general recipe question also showed that the model could infer user intention from very little evidence.
Evidence, such as commit, screenshot, prompt output, or bug: Successful live outputs included a yogurt chicken-curry memory and a Chettinad recipe request. Multiple traces persisted in the Living Archive. Lint and production build passed.
Next small step: Decide whether the AI follow-up question should become a real conversational turn or remain a one-shot prompt.


ENTRY 005

Date: 1 September 2026
Planned task: Resolve the conceptual gap between the AI's follow-up question and the user's inability to answer it.
What was completed: A bounded conversational reconstruction was specified. The user may answer or skip up to three AI questions, then ask the system to organise only their fragments into a Working Family Recipe with visible unknowns.
Choices made and why: The conversation is bounded rather than unlimited. Previous AI text is never treated as recipe evidence. The model acts as interviewer and organiser, while the user remains the source and final authority.
What failed, changed, or surprised me: A conventional regional recipe assistant initially seemed like a useful extension, but it would shift the model into the role of cultural authority and conflict with the research argument. The revised design supports recipe formulation without allowing the model to invent missing cultural knowledge.
Evidence, such as commit, screenshot, prompt output, or bug: docs/conversational-reconstruction-spec.txt and decision-log entry 006.
Next small step: Implement the conversation data model and pure helper functions without changing the visible interface.


ENTRY 006

Date: 2 September 2026
Planned task: Add the live server path for a bounded continued reflection.
What was completed: The reflection endpoint now distinguishes the original one-turn request from the new conversation request. A valid continue action sends labelled user fragments, AI question context, and skipped questions to Gemini and expects a validated reflection response with an explicit type. The original one-turn path remains available.
Choices made and why: Only user-authored fragment text is presented as memory evidence. Questions previously written by the AI are labelled as context only so the model can avoid repetition without converting its own wording into family knowledge. Working recipe generation returns a clear not-yet-implemented response until its separate prompt and schema are built.
What failed, changed, or surprised me: The updated local endpoint passed validation and routing checks, but two live Gemini attempts timed out and returned the safe model-unavailable response. The failed call did not log the API key or memory text and did not require changing the continuation contract.
Evidence, such as commit, screenshot, prompt output, or bug: Fifteen automated tests passed, including new prompt tests for source separation and question repetition. Lint and the production build passed. The health route returned successfully on the temporary test server.
Next small step: Connect the Kitchen interface to the continued reflection request and add answer, skip, and turn-limit states.
